# Памятка по курсу «Рефакторинг баз данных и приложений»

4 курс, Программная инженерия · дистанционный формат · зачёт

## Коротко о курсе

- 8 лекций + 8 практических занятий (объединены в 5 лабораторных работ).
- Аттестация — **зачёт**, без оценки по баллам, но сам зачёт ставится по баллам: **100 баллов всего, зачёт от 60**.
- Все лабораторные выполняются на **одном сквозном проекте** — учебном интернет-магазине книг с намеренно плохим кодом и схемой БД, который вы пошагово улучшаете от работы к работе.
- Стек: **Java 21 + Spring Boot + Spring Data JPA + PostgreSQL + Maven**.
- Проверка **полностью автоматическая** — вручную никто ваш код не читает и оценку не ставит. Оценивает CI на GitHub Actions по объективным гейтам (метрики, тесты, mutation testing, архитектурные правила). Если гейт не проходит — баллы не начисляются, без исключений и без "покажите, я почти сделал".

## Как начать

1. Откройте шаблон-репозиторий: `github.com/itmo-rbdip/rbdip-project-java`.
2. Нажмите **Use this template** → создайте свой репозиторий с именем `rbdip-<ваш_github_логин>` в организации `itmo-rbdip` (или в своём аккаунте — уточните у преподавателя).
3. Клонируйте к себе, поднимите окружение:
   ```
   docker compose up -d
   mvn spring-boot:run
   ```
4. При каждом `git push` автоматически запускается CI — статус (✅/❌) виден прямо в репозитории на GitHub, во вкладке Actions.

## Правила игры

- **Не редактируйте** тесты в пакете `reference` (`src/test/java/.../reference/`) — это эталонные тесты преподавателя, они проверяют, что вы не сломали поведение системы. Их правка не даст баллов, а сломает саму проверку.
- Тесты, которые вы пишете сами (характеризационные тесты, нагрузочные тесты и т.д.) — часть оценки. CI проверяет не просто "тесты зелёные", а что они **реально что-то тестируют** — например, через mutation testing (PIT): если ваш тест не ловит намеренно внедрённую ошибку в коде — балл не засчитывается.
- Репозитории публичные. Это значит, что чужой код технически виден. Работа проверяется по существу (гейты нельзя формально подделать), но списывание — плохая идея для вашего же обучения, а академическая честность остаётся на вашей совести.
- Баллы обновляются при каждом push. Не ждите последнего дня — если что-то не проходит, у вас есть время разобраться, почему.

## Лабораторные работы и баллы

| ЛР | Что делаете | Баллы |
|---|---|---|
| ЛР1 | Находите code/db smells, рефакторите God-класс на несколько классов с чёткой ответственностью, убираете дублирование и magic numbers | 15 |
| ЛР2 | Пишете характеризационные тесты для модуля расчёта цены/скидок + нормализуете схему БД, пишете Flyway-миграции | 20 |
| ЛР3 | Реализуете эволюцию схемы без даунтайма (expand-contract) + пишете нагрузочный тест, подтверждающий отсутствие ошибок во время миграции | 15 |
| ЛР4 | Устраняете N+1 в доступе к данным + выделяете модуль `reviews` по паттерну Strangler Fig, с ArchUnit-проверкой архитектуры | 20 |
| ЛР5 | Финальный полный цикл: весь пайплайн проверок разом, включая mutation testing (PIT) | 30 |

**Зачёт: сумма баллов ≥ 60.**

## Если что-то не работает

Сначала смотрите лог конкретного упавшего шага в Actions — там всегда написано, какой гейт не прошёл и почему (например, `mutation_score=0.32 < 0.6`). Если после этого не разобрались — пишите преподавателю, приложив ссылку на конкретный запуск CI.
